01 / OST

产品概览

OST 是面向 Web 安全测试的 Burp Suite 扩展，将端点扫描、请求处理、参数测试、浏览器重放、指纹识别和身份比较集成在同一工作台。

扫描结果支持检索、条件过滤、本地持久化和导出。可选 MCP 接口用于与本地自动化工具集成。

工作区用途
数据看板查看普通端点扫描结果、导入 URL、控制任务和检查请求响应。
参数扫描为端点配置参数测试计划，并在独立流量列表中查看执行结果。
插件配置管理字典、请求策略、身份、浏览器、范围和存储设置。
指纹管理维护识别条件、输出字段和显示颜色，使用请求响应样本验证规则。
数据收集查看按照配置收集的内容。

Overview

OST is a Burp Suite extension for web-security testing. It combines endpoint scanning, request transformations, parameter testing, browser replay, fingerprinting and identity comparison in one workspace.

Results support search, conditional filtering, local persistence and export. An optional MCP interface connects trusted local automation clients.

WorkspacePurpose
DataboardInspect ordinary endpoint traffic, import URLs and control tasks.
Parameter scanConfigure endpoint-specific parameter tests and inspect their dedicated traffic view.
ConfigManage dictionaries, request policies, identities, browser settings, scope and storage.
FingerprintManage detection conditions, result fields and colors; test rules against paired messages.
CollectReview content collected according to the configured rules.
02 / OST

安装与环境

  1. 使用 Java 21 启动支持 Java 扩展的 Burp Suite。
  2. 在 Extensions → Add 中选择 Java，加载 OST-v1.2.7.jar。
  3. 确认 OST 标签页出现。通过“插件配置 → 其他配置”设置界面语言；重新加载扩展后应用到整个界面。

源码构建在项目根目录执行：

.\mvnw.cmd package
# macOS / Linux
./mvnw package

构建产物位于 extender/target/。加载包含依赖的 OST 包，不使用独立的 extender 包。

普通 Burp 请求无需 Python。浏览器模式需要 Edge 或 Chrome，以及安装了 DrissionPage 的 Python 3.9+ 解释器。

python -m pip install DrissionPage

Installation

  1. Run a Java-extension-compatible Burp Suite with Java 21.
  2. In Extensions → Add, select Java and load OST-v1.2.7.jar.
  3. Open the OST tab. Set the interface language in Config → Other and reload the extension to apply it throughout the interface.

Build from the repository root:

.\mvnw.cmd package
# macOS / Linux
./mvnw package

The artifact is in extender/target/. Load the bundled OST JAR rather than the thin extender JAR.

Burp transport needs no Python. Browser transport requires Edge or Chrome and a Python 3.9+ interpreter with DrissionPage installed.

python -m pip install DrissionPage
03 / OST

基本工作流程

  1. 确定授权测试范围。在 Burp Target Scope 配置允许的目标，并按需开启“主机配置 → 仅扫描 Burp Scope”。
  2. 在请求配置中设置 QPS、延迟、重试和扫描层级。启用所需的字典及请求处理组。
  3. 从 Burp 右键发送请求到 OST，或在数据看板导入 URL，每行一个。选择 Burp 或浏览器请求方式。
  4. 在结果表查看状态码、长度、指纹和身份信息；选中条目查看完整请求与响应。
  5. 对选定端点进行参数扫描或身份重放，将需要进一步验证的请求发送到 Repeater。

主机黑白名单、路径排除和 Burp Scope 是请求范围控制；数据表过滤仅改变结果显示，不控制请求发送。Scope Only 默认关闭，启用后直接使用 Burp 的当前范围设置。

浏览器范围检查针对被拦截的页面请求，不等同于进程级网络隔离。对严格范围项目，应同时配置网络边界。仅对已获授权的系统执行测试。

Workflow

  1. Define authorized targets in Burp Target Scope. Enable Config → Host → Scope Only when required.
  2. Set QPS, delay, retries and scan depth in Request settings. Enable the dictionaries and processing groups needed for the assessment.
  3. Send requests from the Burp context menu or import one URL per line in Databoard. Choose Burp or browser transport.
  4. Review status, length, fingerprints and identity information. Select a row to inspect the paired request and response.
  5. Run parameter tests or identity replay for selected endpoints, and send requests requiring further verification to Repeater.

Host lists, path exclusions and Burp Scope control request eligibility. Table filters only control displayed results. Scope Only is disabled by default and uses Burp's live scope when enabled.

Browser scope checks apply to intercepted page requests, not every process connection. Use network isolation for strict scope requirements. Test only authorized systems.

05 / OST

请求处理

请求处理组由按顺序执行的子规则组成。可添加、编辑、删除或调整子规则，选择请求路径、请求头、请求体或整个请求作为作用范围。

规则类型作用
添加前缀 / 后缀在选定范围添加文本。
匹配替换使用 Java 正则表达式查找并替换文本，支持捕获组引用。
条件检查仅在内容匹配条件时继续执行该组。

非合并组各自从原始请求生成变体；启用“合并”的组按顺序组成一条处理链。没有有效变体时可能使用原始请求。处理后的正文长度由发送流程更新。

内置模板

内置模板默认禁用，启用后参与请求处理。模板与自建规则具有相同的编辑方式。

模板用途
GET to POST替换请求方法。
路径后缀模板生成不同路径形式，评估路由处理行为。
Reflection probe通过查询参数和表单参数的匹配替换规则插入随机标记，配合反射指纹识别输入回显。

反射检测配置

  1. 在请求包处理列表编辑并启用 Reflection probe。组内两个“匹配替换”子规则分别处理查询参数和 POST URL 编码表单，默认优先处理首个查询参数值。
  2. 按测试需求调整子规则的范围、匹配表达式和替换内容。{{nonce}} 在请求变量展开时生成随机值。
  3. 在指纹管理编辑 Reflection candidate 的提取表达式和排除条件。修改标记格式时同步修改该表达式。
  4. 发送请求，结合请求响应内容和指纹结果进行验证。

默认表单模板适用于 application/x-www-form-urlencoded，不处理压缩或分块表单正文。JSON、multipart 等格式可按业务结构配置自己的匹配替换规则。

Request Processing

A processing group contains ordered sub-rules. Add, edit, remove or reorder them, and choose URL, headers, body or the whole request as the scope.

RulePurpose
Add prefix / suffixInsert text at the boundary of the selected scope.
Match and replaceApply a Java regex replacement, including capture-group references.
Condition checkContinue the group only when the content matches its condition.

Non-merged groups generate independent variants from the original request. Enabled merged groups form one ordered pipeline. If no effective variant exists, the original request may be used. The sending pipeline updates body length.

Built-in Templates

Templates are disabled by default and use the same editors as custom rules.

TemplatePurpose
GET to POSTReplace the request method.
Path suffix templatesGenerate alternative paths to assess routing behavior.
Reflection probeInsert a random marker using query/form match-and-replace rules and correlate reflected input with a fingerprint.

Reflection Configuration

  1. Edit and enable Reflection probe. Its two Match and replace sub-rules cover query parameters and POST URL-encoded forms; the default query rule takes precedence.
  2. Adjust each rule's scope, match expression and replacement as required. {{nonce}} produces a fresh value during request variable expansion.
  3. Edit the extraction expression and exclusions in the Reflection candidate fingerprint. Update the expression when changing the marker format.
  4. Send the request and inspect its paired response and fingerprint result.

The default form template supports application/x-www-form-urlencoded, excluding compressed or chunked form bodies. Define custom match-and-replace rules for other structures such as JSON or multipart.

06 / OST

参数扫描

从端点列表选择目标并进入参数扫描，为各端点指定模式、字典、方法和请求方式。配置保存在各自端点上，一批任务可以包含多种模式。

模式配置方式
参数名探测选择参数名和值字典，组合生成参数。
已有参数值测试选择值字典，替换已有参数值。
自定义位置在请求编辑器选择文本并添加编号标记，为每个编号指定字典。

自定义位置支持参数名、参数值和正文片段。相同编号共用一个值，不同编号使用字典组合。

GET /items?category=$1$&page=$2$ HTTP/1.1

Position 1: categories
Position 2: page-numbers

通过位置列表删除标记、清除全部标记或恢复原始请求。自定义位置按字典原文替换，应按目标格式准备 URL 编码、JSON 引号或其他必要结构。

生成计划预览后开始扫描，在“扫描流量”查看进度和请求响应。单批计划上限为 5000 个请求。路由状态筛选排除 404/410，但不代替业务层面的有效性判断。

参数扫描不再次应用普通目录扫描和请求包处理组。浏览器请求可指定 Browser ID；独立队列共享全局暂停及限速，同一 Browser ID 内串行执行。

Parameter Scanning

Select endpoints and open Parameter scan. Configure each endpoint's mode, dictionaries, methods and transport. A batch can contain multiple independently configured modes.

ModeConfiguration
Name discoveryChoose parameter-name and value dictionaries.
Existing valuesChoose a value dictionary to substitute existing values.
Custom positionsSelect text in the request editor, insert numbered markers and assign a dictionary to each position.

Positions may cover names, values or body fragments. Repeated IDs share a value; distinct IDs form dictionary combinations.

GET /items?category=$1$&page=$2$ HTTP/1.1

Position 1: categories
Position 2: page-numbers

Use the position list to remove markers, clear them or restore the original request. Custom substitution is literal: prepare URL encoding, JSON quotes and other structure as required.

Preview the plan, start the scan and inspect progress and paired messages in Scan traffic. A batch is limited to 5,000 planned requests. Route-status filtering excludes 404/410 but is not a business-level validity check.

Parameter scans do not reapply ordinary directory or request-processing groups. Browser requests may select a Browser ID. Separate queues share global pause and rate controls; requests within one Browser ID are serialized.

组合案例：多位置参数 Fuzz

目标：在固定搜索路由上组合两个关键词和两个页码，保留其余请求内容。此案例与动态变量展开独立，也可沿用上例已生成的具体请求头。

  1. 在“字典配置”创建两个 Payload 字典，每行一项：search-terms 填写 apple、orange；page-numbers 填写 1、2。
  2. 在参数扫描中选定已授权端点，使用“自定义位置”，选择 GET 和 Burp 请求。将参数值替换为编号位置，保留请求头后的空行：
GET /search?q=$1$&page=$2$ HTTP/1.1
Host: example.test
X-Tenant-ID: demo-a

3. 在位置列表为编号 1 选择 search-terms，编号 2 选择 page-numbers。

4. 预览应生成 2 × 2 = 4 个请求，再开始扫描：

qpage
apple1
apple2
orange1
orange2

5. 在“参数扫描 → 扫描流量”检查进度及四种组合的请求响应。执行顺序可受并发影响；X-Tenant-ID 应保持 demo-a。

若租户也要参与穷举，可将其值标记为第三个位置并绑定包含两个租户的 Payload 字典，总计 2 × 2 × 2 = 8 个组合。相同编号重复出现时共用一个值，不会增加组合维度。更换为 POST 时应保留目标接口真实的 Content-Type 和正文结构，再标记所需位置。

参数 Fuzz 不展开动态变量。不要把 {{nonce}} 或 {{value.tenant}} 当成此模板中的自动取值；需要变化的内容应绑定位置字典。沿用普通扫描得到的追踪头时，其已生成的值会被保留，不会每个参数请求重新生成。

Worked Example: Multi-position Parameter Fuzz

Goal: combine two search terms with two page numbers on a fixed route while retaining the rest of the request. This workflow is independent of dynamic expansion and can reuse concrete headers produced by the dynamic-header example.

  1. Create two Payload dictionaries in Payload settings, one entry per line: search-terms with apple and orange, and page-numbers with 1 and 2.
  2. Select the authorized endpoint in Parameter scan, choose Custom positions, GET and Burp transport. Replace the parameter values with numbered positions and retain the blank line after the headers:
GET /search?q=$1$&page=$2$ HTTP/1.1
Host: example.test
X-Tenant-ID: demo-a

3. Assign position 1 to search-terms and position 2 to page-numbers.

4. Preview should produce 2 × 2 = 4 requests; then start the scan:

qpage
apple1
apple2
orange1
orange2

5. Inspect progress and the four request/response pairs in Parameter scan → Scan traffic. Concurrency can affect execution order; X-Tenant-ID should stay demo-a.

To enumerate tenants too, mark the header value as a third position and assign a two-tenant Payload dictionary, producing 2 × 2 × 2 = 8 combinations. Repeated occurrences of the same ID share a value and add no combination dimension. For POST, retain the endpoint’s actual Content-Type and body structure, then mark the required positions.

Parameter Fuzz does not expand dynamic variables. Do not expect {{nonce}} or {{value.tenant}} to resolve in this template; assign changing content to position dictionaries. Trace headers inherited from ordinary scans retain their concrete value rather than regenerating for each parameter request.
07 / OST

字典与变量

Payload 字典用于路径与参数测试；变量字典为命名变量提供取值列表。两类字典分别管理：参数扫描选择 Payload 字典，命名变量关联“变量与字典”中的变量字典。

内置随机值

{{nonce}} 无需创建变量或绑定字典。每次变量展开生成 12 字节随机数，输出为 24 个小写十六进制字符。

X-Request-ID: {{nonce}}
X-Request-ID-Copy: {{nonce}}

同一次展开中的两个位置使用相同值，例如 8f3c1a9d7b2e4f6081a5c9d0。不同次展开独立生成；它不是扫描任务 ID，也不保证重试、重放或所有处理阶段共享同一个值。已替换成普通文本的值不会在后续阶段自动刷新。

以下变量由普通请求处理流程提供，不需要在变量列表中创建。域名示例采用 api.dev.example.com，端口为 8443。

自定义动态变量

  1. 使用字典策略时，先在“变量与字典”创建变量字典，每行一个值。
  2. 新增命名变量，填写名称、策略与来源，并启用。名称支持 1–64 个字母、数字、点、下划线或连字符。

适用范围

位置行为
普通请求头、路径 Payload、请求处理规则支持对应处理阶段的上下文变量、命名变量和随机值。多个处理阶段可分别展开。
Profile 局部变量{{profile.tenant}} 在显式 Profile 重放时从该身份的变量表取值；不能替代全局命名变量。
参数 Fuzz 模板与字典按模板与字典原文构造，不展开 {{nonce}}、{{random.*}} 等动态变量，也不重新套用全局请求头、普通请求处理组或 Profile。

不存在、禁用、空值或循环引用的命名变量会使严格展开失败。普通请求启用请求头替换时，含未解析命名变量的头行可被丢弃后继续发送；请求行或正文中未解析的命名变量仍会阻止该变体。始终以扫描流量中的实际请求为准。

Profile 示例：在某个身份的“变量”中填写 tenant=demo-a，其 Header 覆盖中填写 X-Tenant-ID={{profile.tenant}}。这里使用 key=value 格式，与普通请求头列表的 Header: value 格式不同。

Dictionaries and Variables

Payload dictionaries supply path and parameter tests; variable dictionaries supply named variables. They are separate collections: Parameter scan selects Payload dictionaries, while named variables use dictionaries managed in Variables.

Built-in Random Value

{{nonce}} needs no variable definition or dictionary. Each variable expansion generates 12 random bytes, represented as 24 lowercase hexadecimal characters.

X-Request-ID: {{nonce}}
X-Request-ID-Copy: {{nonce}}

Both occurrences share a value within one expansion, for example 8f3c1a9d7b2e4f6081a5c9d0. Separate expansions generate independently. This is not a scan-task ID and does not guarantee a shared value across retries, replays or processing stages. A value already replaced with literal text is not automatically refreshed later.

Request Context Variables

  1. For a dictionary strategy, create a variable dictionary in Variables with one entry per line.

身份重放与比较

在“请求配置 → 身份 Profile”管理测试身份。Profile 支持 Cookie、Header、Query、Body 和局部变量配置。键值配置每行填写 key=value；Cookie 可填写原始值或完整 Cookie 头。

  1. 创建并启用测试身份。
  2. 从 Burp 右键选择 Profile 重放，明确选择本次使用的身份。
  3. 在结果中选择同一请求变体的不同身份记录，执行响应比较。

比较结果用于定位状态、长度、正文及 JSON 字段差异，权限结论仍需结合对象归属和业务规则判断。浏览器 Profile 重放隔离身份 Cookie。

身份凭据可能保存在本地配置、原始请求和导出数据中。使用测试账号并妥善保护工作目录。

Identity Replay

Manage test identities in Config → Request → Identity profiles. Profiles support Cookie, Header, Query, Body and local variables. Enter key/value overrides as one key=value pair per line. Cookie accepts either its value or a complete Cookie header.

  1. Create and enable the test identities.
  2. Choose Profile replay from the Burp context menu and select the identities for this operation.
  3. Select results from the same request variant under different identities and compare responses.

Comparison highlights status, length, body and JSON differences. Authorization conclusions require business context and object ownership. Browser Profile replay isolates identity cookies.

Credentials can appear in local configuration, raw requests and exports. Use test accounts and protect the working directory.

浏览器请求

浏览器模式通过 DrissionPage 驱动 Edge 或 Chrome，用于需要浏览器会话或客户端执行环境的请求。

  1. 在浏览器配置中选择已安装 DrissionPage 的 Python 解释器及浏览器路径。
  2. 设置超时、静态资源加载和目标主机规则。
  3. 在发送或导入请求时选择浏览器方式，并按任务需要区分 Browser ID。
  4. 检查返回的业务响应；涉及挑战页面时结合 Cookie 与响应内容确认会话状态。

599 Browser Bridge Error 表示本地浏览器桥接失败。检查所选解释器、依赖、可执行文件路径及超时设置。

Browser Requests

Browser transport drives Edge or Chrome through DrissionPage for requests requiring a browser session or client-side execution.

  1. Select a Python interpreter with DrissionPage installed and configure the browser executable.
  2. Set timeout, static-resource loading and target-host rules.
  3. Choose browser transport when sending or importing requests, and assign Browser IDs according to the session requirements.
  4. Inspect the application response and, where challenges are involved, verify cookies and session state.

Browser IDs separate browser sessions. Choose appropriate identity and session settings for each task. Browser traffic differs from ordinary HTTP replay; scope management must account for subresource loading.

599 Browser Bridge Error indicates a local bridge failure. Check the selected interpreter, dependencies, executable paths and timeout.

指纹识别与结果过滤

指纹组由数据源、字段、匹配方法和匹配内容组成。组内条件使用 AND，多个组使用 OR。识别结果写入所选字段并应用指定颜色。

  1. 在指纹管理创建或编辑规则，选择请求或响应字段。
  2. 配置相等、包含、正则或对应排除条件。
  3. 填写输出字段和颜色，并使用配对的请求响应样本测试。

关联请求的匹配

containsRequestMatch 使用“匹配内容”中的正则从当前请求提取文本，再检查所选字段是否包含该文本。存在捕获组时使用第一个捕获组，否则使用整个匹配；无匹配或空值不命中。

内置 Reflection candidate 使用此方法检查响应正文，同时要求 2xx、HTML/XHTML、非附件，并排除常见错误或挑战页面。提取表达式、状态条件、内容条件和颜色均可编辑。

反射结果是输入回显线索，不表示已确认 XSS。默认排除条件属于启发式筛选，应根据业务响应调整。

结果过滤

数据看板的指纹和身份过滤支持列表选择及手动输入。聚合指纹按单个命中匹配；原指纹列按完整字段文本匹配。跨字段条件为 AND，同字段条件按界面顺序组合。

Fingerprints and Filters

Fingerprint conditions define a data source, field, method and expression. Conditions within a group use AND; multiple groups use OR. Matching rules populate configured output fields and colors.

  1. Create or edit a rule and select request or response fields.
  2. Configure equality, containment, regex or exclusion conditions.
  3. Set output fields and color, then test using paired request and response samples.

Request-Correlated Matching

containsRequestMatch extracts text from the current request using the regex in the content field, then checks whether the selected field contains it. It uses the first capture group when present, otherwise the full match. Missing or empty matches do not qualify.

The bundled Reflection candidate applies this method to the response body and adds 2xx, HTML/XHTML, non-attachment and common error/challenge exclusions. Extraction patterns, status/content conditions and colors are editable.

A reflection result is an input-echo lead, not confirmed XSS. Default exclusions are heuristic and should be adapted to the application.

Result Filtering

Databoard fingerprint and Profile filters support dropdown selection and manual values. The aggregate fingerprint field matches individual hits; original fingerprint columns compare the full field text. Different fields use AND, while conditions within a field combine in display order.

MCP Integration

MCP is disabled by default. When enabled, the panel displays the local endpoint and service status. Clients can read status, manage supported configuration and submit scan operations. Treat MCP as a privileged control interface for trusted local clients only; do not expose it publicly.
